# NetSentinel: Simulation-Based Network Performance Monitoring Dashboard

*(Dashboard name: **NetPulse**)*

> **All data is simulated.** No physical router, switch, server or SNMP agent is monitored. Every value is generated by a Python simulation engine.

## 1. Abstract
NetSentinel is a web-based Network Management System (NMS) mini-project. A Flask backend simulates six network devices and produces deterministic performance metrics for three scenarios (normal, warning, critical). It calculates a 0-100 network health score, generates threshold-based alerts and gives recommendations. A browser dashboard shows summary cards, a device table and Chart.js charts.

## 2. Problem Statement
Administrators who check devices one by one waste time and miss abnormal conditions. A central dashboard that visualizes metrics, scores health, raises alerts and suggests actions reduces that effort.

## 3. Objectives
- Simulate network devices and their performance metrics.
- Visualize metrics in a responsive dashboard.
- Calculate a transparent health score.
- Detect threshold violations and raise alerts.
- Provide recommendations based on detected problems.

## 4. Features
- Sidebar navigation: Overview, Devices, Performance analytics, Alerts, Settings and info.
- Seven summary cards (devices, online, issues, latency, bandwidth, packet loss, health score).
- Device table (6 devices) with working search and status filter.
- Five Chart.js charts: latency over time, bandwidth by device, CPU by device, inbound/outbound traffic, status distribution.
- Health score ring with per-component breakdown.
- Alerts with severity, device, description, value, threshold, timestamp and recommended action.
- Scenario buttons: Normal, Warning, Critical, Refresh Metrics, Reset Dashboard.
- Clearly labelled simulated data; browser clock labelled as browser time.

## 5. Technology Stack
Python 3, Flask, HTML5, CSS3, JavaScript (no build tools), Chart.js 4.4.1 (via CDN), JSON REST API.

## 7. Software Requirements
Windows 10/11 (or any OS), Python 3.9+, a modern browser (Chrome, Edge, Firefox). **Internet is needed only to load Chart.js from the CDN.** If it is unreachable, the cards, table and alerts still work and a message is shown in place of the charts.

## 8. Installation on Windows
1. Install Python from python.org and tick **"Add Python to PATH"** during setup.
2. Open PowerShell and move to the project folder:
   ```powershell
   cd path\to\network_performance_dashboard
   ```
3. Install dependencies:
   ```powershell
   python -m pip install -r requirements.txt
   ```
   **If `python` is not recognised**, use the Windows launcher instead: `py -m pip install -r requirements.txt` and later `py app.py`.

## 9. Running (PowerShell or VS Code)
- **PowerShell:** `python app.py` (or `py app.py`)
- **VS Code:** File > Open Folder, open the project, press ``Ctrl+` `` for the terminal and run the same command.

Optional: run the tests with `python -m unittest -v`.

## 10. Opening in the Browser
Open **http://127.0.0.1:5000**. Press `Ctrl+C` in the terminal to stop the server.

## 11. API Endpoints
All responses use `{"success": bool, "message": str, "data": object|null}`.

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | Dashboard page |
| GET | `/api/metrics` | Current devices, summary, health, alerts, recommendations, history, thresholds (does not change state) |
| GET | `/api/alerts` | Alerts and recommendations only |
| GET | `/api/thresholds` | Configured alert thresholds |
| POST | `/api/simulate/normal` | Activate the normal scenario |
| POST | `/api/simulate/warning` | Activate the warning scenario |
| POST | `/api/simulate/critical` | Activate the critical scenario |
| POST | `/api/simulate/reset` | Back to the initial normal state and fresh history |
| POST | `/api/refresh` | New simulated sample of the current scenario |

Errors: unknown scenario returns **404**, wrong HTTP method returns **405**, unexpected failures return **500**, all as JSON.

## 12. Health Score Algorithm
Each metric is converted to a sub-score from 0 to 100: 100 at or below the *good* value, 0 at or above the *bad* value, linear in between.

| Component | Good | Bad | Weight |
|---|---|---|---|
| Latency (ms) | 20 | 200 | 0.20 |
| Packet loss (%) | 0.5 | 6 | 0.25 |
| CPU (%) | 40 | 100 | 0.15 |
| Memory (%) | 50 | 100 | 0.10 |
| Bandwidth (%) | 50 | 100 | 0.15 |
| Availability | online / total devices x 100 | | 0.15 |

For each metric, sub-scores are computed per reachable device, then combined as `0.7 x average + 0.3 x worst device` so one failing device is not hidden by healthy ones. Offline devices are excluded from metric averages but reduce availability.

`score = round( sum(weight x component) )`, clamped to 0-100.

Bands: **90-100 Excellent, 75-89 Good, 50-74 Warning, 0-49 Critical.** With the supplied scenario data the scores are about **97 (normal), 70 (warning), 38 (critical)**.

## 13. Threshold-Based Alerts
Thresholds are in `THRESHOLDS` in `app.py`:

| Metric | Warning above | Critical above |
|---|---|---|
| CPU | 80% | 95% |
| Memory | 85% | 95% |
| Latency | 100 ms | 200 ms |
| Packet loss | 2% | 5% |
| Bandwidth | 80% | none |
| Device offline | n/a | always critical |

Alerts are generated from the current metrics on every request. Critical is checked first, so a metric never gets both a critical and a warning alert (one alert per device per metric). An offline device gets a single alert. Device status: Offline > Critical > Warning > Online.

## 14. Sample Testing Scenarios
1. **Start:** normal, no alerts, "Excellent", positive recommendation.
2. **Warning Scenario:** 6 warning alerts and no critical ones (Core Router CPU and bandwidth, Access Switch bandwidth, Application Server memory and latency, Database Server packet loss); score about 70 (Warning).
3. **Critical Scenario:** Access Switch Offline, critical latency, packet loss, CPU and memory, score about 38 (Critical).
4. **Refresh Metrics:** values change slightly but stay in the same scenario band.
5. **Reset Dashboard:** back to normal and history cleared to the initial points.
6. **Devices tab:** search "server" or filter "Offline" and watch the table change.
7. Run `python -m unittest -v` (10 automated tests).

## 15. Limitations
- Simulated data only; no SNMP, ICMP or real device polling.
- State is held in memory and lost on restart; no database or login.
- One shared state for all browser tabs; no automatic live refresh (use the buttons).
- Chart.js is loaded from a CDN.

## 16. Future Enhancements
